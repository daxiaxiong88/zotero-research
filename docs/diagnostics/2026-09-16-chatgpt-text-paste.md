# ChatGPT 知识沉淀：长文字变成附件后被误报未填入

状态：本地修补，未发布。只修改网页连接脚本，不涉及 XPI。
脚本头仍为当前发布系列 1.0.21；本地修补可由诊断中的
`runtime.sourceRevision = chatgpt-text-paste-1` 区分，不能仅凭版本号认定已更新。

## 证据与根因

用户截图显示，ChatGPT 输入区已经出现“已粘贴的文本”卡片，而编辑器为空。
`fillInput()` 在网页接收 paste 事件后，只接受编辑器文字与完整提示词匹配。
因此即使卡片就绪、发送按钮可用，仍在 5 秒后抛出
“ChatGPT 已接收文字粘贴，但输入框尚未完成更新”。这发生在发送前，不是回答回传超时。

实际函数回归命令：

```powershell
node --test --test-name-pattern="ChatGPT long pasted-text attachment" tests-js/userscript.test.cjs
```

修复前确定失败（约 5.1 秒，错误与截图一致），修复后通过。

## 修复范围

- 仅在 ChatGPT 接收本轮文字 paste 之后，认可同一个输入区域中新出现的文本附件。
- 支持截图中的中文标签和英文 Pasted text；不借用图片预览作为文字发送证明。
- 同步处理填入确认与发送前复核，避免后者再次将长文本插入编辑器。
- 复用附件就绪等待；上传失败则保留明确错误，不点发送，不重复粘贴。
- 拒绝旧卡片重渲染、会话历史、隐藏卡片、其他输入区域和无关草稿。
- 记录输入方式、字符数和附件数；完整提示词只用于本轮匹配，不写入诊断。
- 不截短知识沉淀记录，不更改 Gemini、API、回传或公式渲染规则。

## 验证与用户更新

JavaScript 全套 256 项通过；Python 全套 103 项通过，2 项因 Windows 符号链接权限跳过。
Chromium / Firefox 各验证 2 项长文本知识沉淀和 2 项原有图片发送流程：
附件只投递一次、只点击一次发送，首尾历史均保留，完整答案与公式返回侧栏。
浏览器集成使用自有隔离页面，所有 URL 被拦截，并非真实登录账号实测。

在 Tampermonkey 编辑原有脚本，使用本地 `userscripts/zotero-research-webai.user.js`
的全文覆盖并保存，然后刷新 ChatGPT 页面。无需重装 Zotero XPI。
若上次失败的文本卡片仍留在网页输入区，先手动发送或移除它，避免重试叠加旧草稿。
